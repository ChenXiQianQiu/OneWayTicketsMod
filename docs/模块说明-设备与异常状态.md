# 模块说明 · 设备与异常状态

对应代码：`src/OneWayTicketsMod/Game/DeviceGuardService.cs`、`src/OneWayTicketsMod/Patches/DeviceOutlierPatch.cs`、`src/OneWayTicketsMod/UI/TabDevice.cs`

## 1. 什么是「设备异常」

`Device.DeviceState`（`Decompiled/World/World.Devices/Device.cs:21-30`）：

| 枚举 | 中文 | 表现 |
|---|---|---|
| `normal` | 正常 | — |
| `immue` | 免疫中 | 刚清掉异常后的短暂无敌，时长 `Config.device_debuff_immue_duration` |
| `fired` | 燃烧 | `DeviceFired`，持续掉血 |
| `stupor` | 机械故障 | `DeviceStupor`，设备停摆 |
| `acid` | 腐蚀 | `DeviceAcid`，持续掉血 |
| `bind` | 缠绕 | `Adherent` 附着，`WorldContext.slow_rate` 上升 |
| `wet` | 潮湿 | `DeviceWet`，攒水滴 |

## 2. 唯一入口：`ITarget.applied_outlier`

```csharp
// Device.cs:795
void ITarget.applied_outlier(ITarget source, string outlier_type, int value)
{
    if (state == DeviceState.immue) return;
    switch (outlier_type)
    {
        case "sharp": break;              // 空分支
        case "flash": break;              // 空分支
        case "blunt": ... state = stupor; // 钝击，按概率
        case "fire":  ... state = fired;  // 还会和 wet 互相抵消
        case "acid":  ... state = acid;
        case "wrap":  ... AddEmergency("wrap", 999f);
        case "water": ... state = wet;    // 也会和 fired 互相抵消
    }
}
```

所有伤害流程最后都会调它（`Enemy_Hurt_Helper`、各 `*Projectile`、`Weather`、
`AdherentMgr`、各 `Device_AI` 的攻击逻辑、控制台 `buffdevice`），
所以**拦掉这一个方法就等于设备永远不会进异常状态**，不用逐个改调用方。

而它的**第一行**就是：

```csharp
if (state == DeviceState.immue) return;
```

于是还有一条更省事的路：**不用拦方法，只要让设备一直处于 `immue`**，
所有异常类型就都进不来。v0.2.2 正是这么做的（原因见第 2.2 节）。

## 2.1 为什么补丁不能写死方法名

这是**显式接口实现**，编译后的方法名是 `World.ITarget.applied_outlier`
（带命名空间点号），而且它是 `private virtual`。所以：

```csharp
[HarmonyPatch]
static class DeviceOutlierPatch
{
    // 按后缀反射找，不依赖名字拼写
    static MethodBase TargetMethod() =>
        AccessTools.GetDeclaredMethods(typeof(Device))
            .FirstOrDefault(m => m.Name.EndsWith("applied_outlier", StringComparison.Ordinal));

    [HarmonyPrefix]
    static bool Prefix() => !DeviceGuardService.ImmuneEnabled;
}
```

已用离线反射验证过实际名字：

```
World.Devices.Device → 'World.ITarget.applied_outlier'  private=True virtual=True
```

`Device` 的所有子类（`BasicWheel`、`DScript_Shooter_*`、`Unique_War_Drum` …）
都**没有**重写这个方法（全量 grep 确认），所以补丁对全部设备生效。

> `Boomerang`、`Enemy`、`Caravan` 也各有一份空的 `applied_outlier`，
> 但它们是各自独立实现 `ITarget` 的类型，与设备无关，不用管。

## 2.2 v0.2.2：补丁不执行 → 改成轮询钉住 `immue`

v0.2.0/v0.2.1 的免疫靠上面那个 Harmony 前置补丁，实测**完全不执行**
（本作 Harmony 整体失效，见 `docs/模块说明-旅人与工位.md` 4.1），
所以玩家开着开关，设备照样会烧起来、被腐蚀。

现在改为 `DeviceGuardService.Tick()`（由 `PanelHost.OnTick` 每帧调用，0.2 秒节流）：

```csharp
foreach (var slot in DeviceMgr.slots_device)
{
    var d = slot.slot_device;
    if (d == null) continue;

    if (d.device_emergency != null) d.EnterSafeArea();   // ① 先清掉已经挂上的异常（图标一起消失）
    d.state = DeviceState.immue;                          // ② 钉免疫：applied_outlier 第一行就 return
    immu_countdown = 999999;                              // ③ 续上倒计时，见下
}
```

③ 是必须的：`CheckEmergency`（`Device.cs:392-402`）每 tick 会做

```csharp
if (state == DeviceState.immue) { immu_countdown--; if (immu_countdown <= 0) state = normal; }
```

`immu_countdown` 是**私有字段**，用反射 `GetField("immu_countdown", NonPublic|Public)`
拿一次缓存起来，每轮写 `999999`，这样即使 0.2 秒才刷一次也绝不会掉回 `normal`。
（万一某个版本字段改名了，反射拿不到只会退化成「异常闪一下就消失」，
日志里会写一条警告，不会崩。）

关掉开关时 `SetEnabled(false)` → `RestoreAll()`：把所有 `immue` 的设备改回 `normal`、
`immu_countdown` 清 0，避免残留。

**安全性核对**（全量 grep `DeviceState` 的使用点）：

| 使用点 | 对 `immue` 的反应 |
|---|---|
| `applied_outlier` | 直接 return（这就是我们要的） |
| `DeviceUiView.attach` | **会炸**：`state != normal` 时调 `show_emergency(device_emergency)`，`immue` 下 emergency 是 null，而方法最后一行 `de.init()` 没判空 → `NullReferenceException`。详见 2.3 |
| `DScript_*` 的 AI | 只判断 `state != stupor`，`immue` 视为可用 → 设备照常工作 |
| `Relic_Melee_Arrow_Chasing/Period` | 明确接受 `normal` 或 `immue` |
| `PlayerToolMgr` / `CircleSaw` | 只认 `wet` / `acid` / `fired` / `bind` → 相关工具会因为没异常而用不上（作弊的必然结果） |

## 2.3 v0.2.3：`immue` + 进安全区 = 黑屏（真 bug，已修）

**现象**：开着「设备免疫异常状态」时，一进安全点就整屏黑，按什么都没反应，
但游戏逻辑还在跑（Mod 面板还能按 F1 打开，设备页显示「免疫中 5 台」）。

**日志证据**（`BepInEx/LogOutput.log`，已打开 `WriteUnityLog`）：

```
NullReferenceException: Object reference not set to an instance of an object
World.Devices.DeviceUiViews.DeviceUiView.show_emergency (DeviceEmergency de)
World.Devices.DeviceUiViews.DeviceUiView.attach (Device owner)
Foundations.MVVM.Model`2[T,V].add_view (V view)
World.Devices.Equip.EquipSlot.set_panel (Device device)
World.Devices.Equip.EquipSlot.init ()
World.Devices.Equip.EquipmentMgr.Init (System.String[] devices_id)
World.Business.DeviceBusinessPanel.Init (System.UInt32 business_id, System.Int32 scene_index)
World.SafeArea.SafeAreaView.init_device (...)
World.SafeArea.SafeAreaView.init_shop (...)
World.SafeArea.SafeAreaView.Init ()
World.WorldSceneRoot+<IBlackScreenCoroutine>d__47.MoveNext ()
```

**因果链**：

1. 免疫把 `state` 钉成 `immue`，此时 `device_emergency == null`；
2. 进安全区 → `SafeAreaView.Init()` → `init_device`（生成设备商店）
   → `EquipmentMgr.Init` → `EquipSlot.set_panel(device)` → `DeviceUiView.attach(device)`；
3. `DeviceUiView.attach`（`DeviceUiView.cs:67-69`）：
   ```csharp
   if (owner.state != Device.DeviceState.normal)
       show_emergency(owner.device_emergency);   // immue 时传进去的是 null
   ```
4. `show_emergency`（同文件 201-235）末尾：
   ```csharp
   de.init();                                    // ← 没有判空
   ```
   → `NullReferenceException`；
5. 异常穿出 `SafeAreaView.Init()`，`IBlackScreenCoroutine` 直接终止 →
   `black_screen` 永远停在 `alpha = 1`，`ban_esc` 也一直是 `true`。

**修法**（`DeviceGuardService.Tick`）：

```csharp
bool inSafeArea = ctx != null && ctx.in_safe_area;
if (inSafeArea != _wasInSafeArea)
{
    _wasInSafeArea = inSafeArea;
    if (inSafeArea) RestoreAll();   // 进安全区第一帧就全部还原成 normal
}
if (inSafeArea) return;             // 安全区里不钉
```

时序上是安全的：`Safe_Area_Helper.enter()` 先设 `in_safe_area = true` 再靠协程淡入，
而协程要 75 帧（约 0.6 秒）才走到 `safe_area.Init()`，
`PanelHost.Update`（60Hz，约 36 帧）有充足时间完成还原。

**教训**：给游戏对象钉「非正常状态」之前，一定要把所有 `state != normal` 分支都读一遍。
`DeviceUiView.attach` 这种「只在换设备 / 开商店时才走」的分支很容易被漏掉，
而且它一旦抛异常，炸的是**别人的协程**（这里是进安全区的黑幕协程），
现象和「状态逻辑」看起来毫无关系。

## 3. 只免疫异常，不免疫掉血

`Device.Hurt`（`Device.cs:486`）是另一条链路：

```
ITarget.hurt → Hurt_Calc_Helper.dmg_to_device → Device.Hurt(dmg)
```

伤害照常扣 `current_hp`，扣到 0 会 `Disable()`（设备报废）。
要「设备不掉血」请用「局内」页的**无限耐久**（那是补车辆耐久的）——
设备本体没有轮询修复的开关，因为设备血量每局重建，改了意义不大。

## 4. 一键清除

`DeviceGuardService.ClearAll()` 对每台异常设备调用 `Device.EnterSafeArea()`
（`Device.cs:279`）—— 这正是游戏进安全区时的清理逻辑：

1. `device_emergency` 逐个 `view.notify_remove_emergency(...)` → **UI 图标一起消失**；
2. `state = DeviceState.normal`。

比手动 `state = normal` 安全得多：后者会留下没被移除的 emergency 对象，
下次 tick 的 `CheckEmergency` 会把它又捡回来。

> `DScript_Melee_Charge` / `DScript_Ram` / `DScript_Special_Boomerang`
> 重写了 `EnterSafeArea()`，但都先调 `base.EnterSafeArea()`，所以行为一致。

## 5. 设备列表怎么读

```csharp
SingletonAccess.Mgr<DeviceMgr>("DeviceMgr")   // Mission 里挂名 "DeviceMgr"
  └── slots_device : List<DeviceSlot>
        └── slot_device : Device   // 可能是 null（拆掉了）
```

- 名字：`device.desc.name` 是本地化 key，要过 `Localization_Utility.get_localization`，
  再把 `<sprite ...>` 之类的富文本标签剥掉（IMGUI 不解析）。
- 状态：直接读 `device.state`，由 `TabDevice.StateName` 映射成中文。
- 报废判定：`is_validate == false`（`Disable()` 里置的），列表里用红色显示。

## 6. 已知取舍

| 取舍 | 说明 |
|---|---|
| 设备会一直显示「免疫中」 | 这是本 Mod 钉住的状态，面板「免疫中 N 台」就是这个数；关掉开关立刻变回「正常」 |
| 缠绕（`wrap`）仍然会生成 `Adherent` 对象 | 免疫拦的是「设备进入 bind 状态」，`AdherentMgr` 自己的附着逻辑不受影响，但设备不会显示缠绕、也不会吃 `slow_rate` 之外的减益 |
| 相关工具会「没得用」 | 灭火器 / 除酸等工具靠 `state == fired/acid` 判断可用，设备一直免疫时这些工具没有目标 |
| 开关持久化 | `Plugin.DeviceImmune` 写进配置文件，重启游戏仍生效 |
| `Patches/DeviceOutlierPatch.cs` 保留但无效 | 本作 Harmony 不执行；留着是为了万一补丁恢复可用，判定会更干净（状态都不进） |
