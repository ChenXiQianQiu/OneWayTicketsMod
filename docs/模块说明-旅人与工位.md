# 模块说明 · 旅人与工位

对应代码：
- `src/OneWayTicketsMod/Game/TeamService.cs`（旅人列表 + 解除操作中人数上限）
- `src/OneWayTicketsMod/Game/CharacterGuardService.cs`（不晕车词缀）
- `src/OneWayTicketsMod/Patches/CharacterShockPatch.cs`（保留的补丁，本作不执行）
- `src/OneWayTicketsMod/UI/TabTeam.cs`（界面）

> v0.2.5 起 `Game/CubicleService.cs` 和 `Patches/CubicleSetPatch.cs` 已删除，
> 原因见第 5 节。

## 1. 三个容易混的概念

| 概念 | 代码位置 | 上限 | 说明 |
|---|---|---|---|
| **操作中** | `CharacterMgr.characters` | 6（v0.2.4 起 Mod 可解除到 12） | 前排旅人，能上工位、能被拖拽 |
| **休息区（局内）** | `CharacterMgr.backup.backup_characters` | 6 | 后备队，有头像能点选，但**上不了工位** |
| **休息区（营地）** | `Camp.Character.CampCharacterRestRoom` + `CommonContext.friend_character_list` | — | 营地里的休息区，靠科技解锁，跟局内不是一回事 |

用户说的「局内那个休息区」= 第二种（`backup_characters`）。

## 2. 为什么休息区旅人上不了工位

`Decompiled/World/World.Helpers/Cubicle_Helper.cs` 第 68 行：

```csharp
if (Character_Helper.GetAllCharacters().Contains(selectCharacter) && selectCharacter != null && ...)
```

而 `GetAllCharacters()`（`Character_Helper.cs:14`）只返回 `mgr.characters`（前排）。
后备队成员永远不在这个列表里 → 判断直接失败 → 点了工位没反应。

顺带一提：后备队旅人**本来就能被点选高亮**，因为 `CharacterBackupView` 复用的也是
`CharacterView`，它的 `OnPointerClick` 会调 `Cubicle_Helper.SetSelectCharacter(character)`
（`Decompiled/World/World.Characters/CharacterView.cs:105`）。缺的只是最后那一道判断。

而且不只是 `SetCubicle` 一条路径只认前排：

| 路径 | 代码 | 只认 characters |
|---|---|---|
| 点选后能不能上工位 | `Cubicle_Helper.SetCubicle`（:68 `GetAllCharacters().Contains`） | 是 |
| 读档恢复工位归属 | `DevicePD.use_current_data`（:88 `characters.Find(...)`） | 是 |
| 存档写工位归属 | `Save_DS.do_save`（:67 `basicCubicle.worker.desc.id`） | 否（但读回来要按 characters 找人） |
| 设备认不认这个人 | `Device.cubicle_list[i].worker != null` | 否（只看 worker 字段） |

所以「绕开一道判定」是没用的，必须让人真的出现在 `characters` 里。

## 3. 先说结论：本作的 Harmony 补丁不执行

v0.2.0 用 Harmony 后置补丁改 `GetAllCharacters` 的返回值，v0.2.1 早期改成接管
`Cubicle_Helper.SetCubicle`，**两个补丁实测都完全没有被执行**。

验证方式：给 `CaravanMover_Run.do` 挂一个计数后置补丁，车连续跑了十几秒，
计数一直是 0；同一套机制挂的 `SetCubicle` 日志也一条都没有。
也就是说 Harmony 在本作里整体失效（推测与 Mono 内联 / 程序集加载方式有关），
而 `BepInEx/LogOutput.log` 里只显示「补丁已挂载」，没有任何报错，很容易误判成生效了。

所以 v0.2.1 起，凡是靠补丁实现的功能都改成不依赖 Harmony 的写法。
（v0.2.5 顺手把已经没用的 `CubicleSetPatch` 删了，日志里只剩三个补丁。）

## 4. 现在的做法（v0.2.4 起）：解除操作中人数上限

思路：不再跟 `SetCubicle` 的判定较劲，**直接把 6 人上限拿掉**，
让整支队伍（最多 12 人）都待在 `characters` 里 —— 游戏自己的点选 / 拖拽流程对所有人都成立。

### 4.1 6 人上限的四个位置

全部在 `Decompiled/World/World.Characters/CharacterMgr.cs`（外加 `Character_Helper.CanAdd`）：

```csharp
AddCharacter      (:139)  if (characters.Count < 6) 进前排；else if (backup.Count < 6) 进后备
AddCharacterByLoad(:180)  同上
TakeCharacterToBackup (:249) if (!characters.Contains(c) || backup.Count >= 6) return;
TakeCharacterToFront  (:273) if (!backup.Contains(c) || characters.Count >= 6) return;
Character_Helper.CanAdd (:70) 前排满 6 → 要求后备 < 6
```

而 `characters`（:41）、`backup`（:73）都是 public 字段，视图列表 `views` 来自
`Foundations.MVVM.Model.views`（`public LinkedList<V>`），
所以绕过上限**不需要 Harmony**，直接动列表 + 手动通知视图即可。

`CharacterMgrView.notify_add_character`（:83）找不到空槽会 `Instantiate` 一个新的
`CharacterView`，所以头像数量本身没有上限（实测 9 人正常排开，没溢出）。

### 4.2 实现（`Game/TeamService.cs`）

```
UnlockFrontLimit = true
  ├── SendToFront(c)：前排 < 6 → mgr.TakeCharacterToFront(c)（游戏原方法）
  │                    前排 >= 6 → PromoteToFront(c)（自己动列表）
  ├── PromoteToFront(c)
  │     characters.Add(c) → NotifyViews(notify_add_character)
  │     backup.Remove(c)  → NotifyViews(notify_backup_character)
  ├── PromoteAll()：休息区所有人一次挪上去（面板「全部上阵」）
  └── Tick()（0.5s）：读档 / 招募 / 换局后把休息区的人自动补回来，
                      玩家手动「换下」的人记在 ManualBackup 里，跳过不拉
```

### 4.3 几个必须记住的点

- **`TakeCharacterToFront` 第一行就 `characters.Count >= 6` 直接 return**，
  所以超过 6 人只能自己动列表；动完必须手动 `notify_add_character`，
  否则数据变了但底部那排头像不变（v0.2.1 就栽在这）。
- 读档时 `CharacterPD.use_current_data` 用 `AddCharacterByLoad` 逐个人加，
  超过 6 个的会被丢进后备队（后备又只有 6 个位，再多就两头都进不去，人会悄悄少），
  所以 `Tick()` 的自动上阵是必须的。
- `Character.Start()` 在本作是空实现（`CharacterProperty.Start` 没有任何子类重写，
  全量 grep 确认），所以从后备队提上来不需要补调 `Start()`。
- 全员在操作中 = 全员参与 `CharacterMgr.tick` 的颠簸判定，嫌吵就把「旅人不会晕车」一起开。

## 4.4 工位格子为什么会在战斗中消失（v0.2.6）

现象：进战斗之后新装 / 换上的设备（例如转轮机枪）工位格子直接不见，只剩空占位框，点也没反应。

链条（全部有反编译依据）：

```
Tech_Unlock_Cubicle.@do                    Tech_Unlock_Cubicle.cs:8-13
  ├── BattleContext.active_cubicle = true      ← 唯一的置 true 点，一次性
  └── DeviceMgr.SetCubicle(hide: false)        ← 把格子显示出来

BattleContext.Init() → reset_context()     BattleContext.cs:351 / :431
  └── active_cubicle = false                   ← 每次场景初始化都清掉（WorldSceneRoot.cs:129）

DeviceUiView.attach                        DeviceUiView.cs:60-66
  └── if (!active_cubicle) 所有 station.SetActive(false)
```

所以：解锁科技之后只要换过一次场景 / 进过一次战斗，`active_cubicle` 就永远是 false，
此后**新建**的设备视图 attach 时格子会被关掉；而早就在场的设备视图是之前建的，格子还开着 ——
这就是「只有某台新设备工位消失」的原因。格子关掉后 `CubicleUiView` 收不到点击，所以也「不让放」。

修法（`Game/CubicleViewService.cs`，面板「设置」页 → 工位显示，默认开启）：
每秒把科技那两行重跑一遍，并在设备数量变化时补一次（新设备的视图可能建在两次轮询之间）：

```csharp
ctx.active_cubicle = true;
mgr.SetCubicle(hide: false);   // = 对每台设备 notify_set_cubicle(false)
```

只影响「格子显不显示」，不碰任何战斗数值；面板上有「立即修复」按钮可以手动触发一次。

## 5. v0.2.5 删掉的两个功能（历史记录）

| 功能 | 曾经的做法 | 为什么删 |
|---|---|---|
| 「休息区旅人也能上工位」开关 | v0.2.1 面板直接绑工位；v0.2.2 改成先 `TakeCharacterToFront` 再走落地流程 | 用户实测**完全没效果**。根因是它绕不过「只认前排」的一整串路径（见第 2 节），而且前排只有 6 个位 |
| 「工位分配」卡片（安排 / 撤下 / 一键上工） | 遍历 `CubiclesMgr.cubicles` 直接 `set_worker` | ① **会把人塞进「已经不在车上」的旧设备工位**：`CubiclesMgr.cubicles` 只增不减地保留了历史设备留下的工位对象，界面上看不出来；② 解除上限后全员都在操作中，游戏自己的点选流程就够了，不需要 Mod 再插一手 |

顺带删掉的：
- `Patches/CubicleSetPatch.cs`（接管 `SetCubicle` 放宽人员判定）—— 它只服务于上面那个开关，本作又不执行；
- `Plugin.RestCharacterEnabled` 配置项 —— 老的 `.cfg` 里可能还留着这一行，BepInEx 会忽略，不影响启动。

CE 时代还有一个坑值得记着：把后备队成员**追加进** `characters` 而不删后备，
会让 `Save_DS` 遍历两边时把同一个旅人写两份，读档变成两个一样的人。
现在 `PromoteToFront` 是「加进前排 + 从后备删掉」，全程只有一份。

## 6. 使用步骤

1. 面板「旅人」页 → 确认「解除操作中人数上限」是「已开启」（默认开）；
2. 需要的话点「全部上阵」立刻把休息区的人换上来（读档后 0.5 秒内也会自动做）；
3. 关掉面板，用游戏自己的方式上工位：点底部「操作中」里的头像 → 点设备下面的工位格。

旅人处于昏迷 / 眩晕（`Character.state != null`）时游戏不允许上工位，
面板「旅人列表」里能看到每个人的状态。

### 6.1 怎么确认真的生效

游戏内点右上角的「交叉刀剑」图标（工位 / 装备面板）：
底部「操作中」那排头像数量会等于旅人总数（例如 9 个人就 9 个头像），
「休息区」那排是空的；设备下面那些小格子里会出现干活的人。

## 7. 晕车（冲击昏迷）与免疫

### 7.1 游戏原本的机制

```
CharacterMgr.tick()                               CharacterMgr.cs:61-72
  ├── character_focus_aceleration 由车辆纵向加速度驱动
  │     （第 56 行还会减去 global_car_shock_absorb 的减震量）
  ├── shockForce = |character_focus_aceleration.y|
  └── 对每个前排旅人：Character.ApplyShockForce(shockForce)

Character.ApplyShockForce                         Character.cs:221-246
  ├── isImmuneToStun / state != null / coma_free_ticks > 0 → 直接返回
  ├── 阈值 num = desc.coma_g * (1 + global_coma_resist_pts/1000)
  ├── shockForce <= num → 不晕（会说一句台词）
  └── shockForce >  num → 按概率写入 state = new Coma(this, ...)
```

要点：

- **`ApplyShockForce` 是全游戏唯一 `new Coma` 的地方**（已全量 grep 确认），
  所以它就是「晕车」的唯一开关点。
- 只有**前排（`mgr.characters`）**旅人会参与这个判定，休息区的不受影响。
- 昏迷结束后 `Coma.end()` 会写 `coma_free_ticks = 3.5 秒 × 120`，
  所以不会「刚醒又立刻晕」。
- 旅人特性 `CP_Step_Up`（挺身而出）在**设备受击**时也会调 `ApplyShockForce`
  （`CP_Step_Up.cs:24-33`），所以同一个入口也负责「被设备震晕」。

### 7.2 本 Mod 的做法（v0.2.1 起：补「油门焊死」词缀）

v0.2.0 是给 `Character.ApplyShockForce` 挂前置补丁跳过整个方法，实测无效
（原因见第 3 节：Harmony 在本作不执行）。

现在改成改数据：给每个旅人补一份游戏自带的 **「油门焊死」** 词缀
（`CP_Reckless_Driving`，运行时从 `propertiess.records` 里按 `script` 名找到，实测 id = 162004）：

```csharp
// CP_Reckless_Driving.cs:16-20
public override void EnterTeam()
{
    owner.isImmuneToStun = true;                                   // ← 这就是免疫晕车
    Singleton<BattleContext>.instance.wheel_tractive_force_role += wheel_tf;
}
```

`CharacterGuardService` 的流程：

| 时机 | 动作 |
|---|---|
| 开关打开 | 对每个旅人：没有该词缀就 `CharacterUtility.GetProperty` → `Init` / `Start` / 加进 `character_properties` / `EnterTeam()`，并记进 `Injected` |
| 每 0.5 秒 | 轮询兜底：新入队、换人、读档后自动补齐（已有词缀的人只确认 `isImmuneToStun = true`） |
| 开关关闭 | 只对 `Injected` 里的人 `ExitTeam()` + 从列表移除，旅人自带的词缀不动 |
| 换局 / 读档 | 检测到 `CharacterMgr` 引用变化就清空 `Injected`（旧 Character 已废弃，不能再调它的 `ExitTeam`） |
| 词缀表还没就绪 | 直接 `isImmuneToStun = true` 兜底，保证功能立刻可用 |

要点：

- 词缀会随存档保存，读档后 `CharacterPD.use_current_data` 会重建 `character_properties`
  并调 `EnterTeam()`，所以免疫效果自动恢复，面板会显示「队伍里 N 人已有」；
- 副作用：词缀本身会给车轮加牵引力（`wheel_tractive_force_role += wheel_tf`），
  这是游戏数据原本的设计，不是本 Mod 加的；
- `isImmuneToStun` 只在 `ApplyShockForce` 里被读，全量 grep 确认游戏里只有
  `CP_Reckless_Driving` 会写它，所以关闭开关时把没词缀的人设回 `false` 是安全的。

### 7.3 「全部唤醒」

`CharacterGuardService.WakeAll()` 遍历前排 + 休息区，对 `state is Coma` 的旅人执行
`state.end(); state = null;` —— 和游戏自然结束昏迷的路径完全一致，
`end()` 会顺手写好 3.5 秒免疫。只清昏迷，不动 `Galvanized`（亢奋）等其它状态。

视图（`CharacterView`）是在 hover / 点击时**按需读** `character.state` 的，
所以清完不需要通知 UI，下一次交互就会显示正常。
