# 模块说明 · 旅人与工位

对应代码：
- `src/OneWayTicketsMod/Game/TeamService.cs`（旅人列表）
- `src/OneWayTicketsMod/Game/CubicleService.cs`（工位分配）
- `src/OneWayTicketsMod/Game/CharacterGuardService.cs`（不晕车词缀）
- `src/OneWayTicketsMod/Patches/CubicleSetPatch.cs`、`Patches/CharacterShockPatch.cs`（保留的补丁，本作不执行）
- `src/OneWayTicketsMod/UI/TabTeam.cs`（界面）

## 1. 三个容易混的概念

| 概念 | 代码位置 | 上限 | 说明 |
|---|---|---|---|
| **操作中** | `CharacterMgr.characters` | 6 | 前排旅人，能上工位、能被拖拽 |
| **休息区（局内）** | `CharacterMgr.backup.backup_characters` | 6 | 后备队，有头像能点选，但**上不了工位** |
| **休息区（营地）** | `Camp.Character.CampCharacterRestRoom` + `CommonContext.friend_character_list` | — | 营地里的休息区，靠科技解锁，跟局内不是一回事 |

用户说的「局内那个休息区」= 第二种（`backup_characters`）。

## 2. 为什么休息区旅人上不了工位

`Decompiled/World/World.Helpers/Cubicle_Helper.cs` 第 68 行：

```csharp
if (Character_Helper.GetAllCharacters().Contains(selectCharacter) && selectCharacter != null && ...)
```

而 `GetAllCharacters()`（`Character_Helper.cs:14`）只返回 `mgr.characters`（前排）。
后备队成员永远不在这个列表里 → 判断直接失败 → 点了工位没反应。

顺带一提：后备队旅人**本来就能被点选高亮**，因为 `CharacterBackupView` 复用的也是
`CharacterView`，它的 `OnPointerClick` 会调 `Cubicle_Helper.SetSelectCharacter(character)`
（`Decompiled/World/World.Characters/CharacterView.cs:105`）。缺的只是最后那一道判断。

## 3. CE 版的做法与副作用

CE 表里是「把后备队成员 **追加进** `characters` 列表」：
`SetCubicle` 能过了，但这个人同时存在于两个列表里 →
`Save_DS` 遍历两边时会把同一个旅人写两份 → 存档再读档变成两个一样的人。

## 4. 本 Mod 的做法（v0.2.2 起：真的把人换到前排）

### 4.1 先说结论：本作的 Harmony 补丁不执行

v0.2.0 用 Harmony 后置补丁改 `GetAllCharacters` 的返回值，v0.2.1 早期改成接管
`Cubicle_Helper.SetCubicle`，**两个补丁实测都完全没有被执行**。

验证方式：给 `CaravanMover_Run.do` 挂一个计数后置补丁，车连续跑了十几秒，
计数一直是 0；同一套机制挂的 `SetCubicle` 日志也一条都没有。
也就是说 Harmony 在本作里整体失效（推测与 Mono 内联 / 程序集加载方式有关），
而 `BepInEx/LogOutput.log` 里只显示「补丁已挂载」，没有任何报错，很容易误判成生效了。

所以 v0.2.1 起，凡是靠补丁实现的功能都改成不依赖 Harmony 的写法。

### 4.2 v0.2.1 的「绕开判定」为什么也不行

v0.2.1 改成面板直接调 `set_worker` / `SetCharacterWorking` / `EnterCubicle`，
数据上确实绑上了（面板里「空闲」变「在岗」），但玩家在游戏里看不出效果：

- 人还在 `backup_characters` 里，底部「操作中」那一排不会多出他；
- 设备的 `cubicle_list[i].worker != null` 虽然成立，但前排以外的旅人
  `Character.Start()` 从没跑过（`CharacterMgr.AddCharacter` 只有前排那条分支调 `Start()`），
  词缀里 `Start()` 注册的东西不会生效；
- 存档 `Save_DS` 写工位归属时读的是 `basicCubicle.worker`，读档重建时又按前排列表对号入座，
  两套列表一旦不一致就会出现「工位空着 / 人不在岗」。

### 4.3 现在的实现：先换人，再上工位

`Game/TeamService.cs` 新增两个方法，直接用游戏自己的换人接口
（`CharacterMgr.cs:249 TakeCharacterToBackup` / `:273 TakeCharacterToFront`）：

```
SendToFront(c)
  ├── 前排没满 6 人 → mgr.TakeCharacterToFront(c)                    // 游戏自带，含视图通知
  └── 前排满 6 人   → PickSwapOut() 挑一个「没在岗、也没占工位」的前排旅人
                       └── backup.Remove(c) → TakeCharacterToBackup(x) → backup.Add(c) → TakeCharacterToFront(c)
SendToBackup(c) → mgr.TakeCharacterToBackup(c)（休息区满 6 人时拒绝并提示）
```

为什么中间要 `backup.Remove(c)` / `backup.Add(c)` 这么绕：游戏这两个方法各带一道判定

```csharp
// CharacterMgr.cs:249
public void TakeCharacterToBackup(Character c)
{
    if (!characters.Contains(c) || backup.backup_characters.Count >= 6) return;   // ← 后备满就什么都不做
    ...
}
// CharacterMgr.cs:273
public void TakeCharacterToFront(Character c)
{
    if (!backup.backup_characters.Contains(c) || characters.Count >= 6) return;   // ← 前排满 / 不在后备就什么都不做
    ...
}
```

前后排都是 6 人时两个条件互相锁死，只能先把 `c` 从后备列表里摘出来腾个位，
换下 `x` 之后再放回去，让 `TakeCharacterToFront` 的 `Contains` 判定能过。
中间这几步只动内存列表、不通知 UI（两个方法内部各自会通知），界面不会闪。

`CubicleService.Assign` 则是「先 `SendToFront`，再走落地流程」：

```csharp
if (!TeamService.IsInFront(c)) TeamService.SendToFront(c, out frontNote);  // 开关关掉时直接拒绝

Cubicle_Helper.EmptyCubicle(bc);                  // 清空目标工位
if (map.TryGetValue(c, out var old)) EmptyCubicle(old);  // 清掉他原来占的工位
map[c] = bc;                                      // 登记到 character_cubicle
bc.set_worker(c);                                 // 绑 worker
mgr.SetCharacterWorking(c, true);                 // is_working = true
c.EnterCubicle(bc);                               // 触发词缀的 EnterCubicle
```

- 全程只有一份，`Save_DS` 不会把同一个人写两份；
- 底部「操作中 / 休息区」两排会真的跟着变（`notify_add_character` / `notify_backup_character`）；
- 开关 `Plugin.RestCharacterEnabled` 关掉后，面板里点「安排」会直接拒绝，
  行为回到游戏原样（游戏内点选本来也上不了）。

### 4.4 界面（v0.2.2 顺手修的布局坑）

旅人列表每行现在是 `位置 / 名字 / 在岗 / 状态 / [上阵|换下] [选]`。

> ⚠️ 行内**不能**用 `GUILayout.FlexibleSpace()` 把按钮推到右边：
> 页面外层滚动区用的是游戏自带的 `GUI.skin.verticalScrollbar`，
> 它的可见宽度比布局宽度窄，行内容按 FlexibleSpace 撑满后，
> 右侧按钮会画到可见区域外面 —— 看得见一部分、点不到（v0.2.1 的「撤下」就是这样消失的）。
> 现在按钮紧跟在状态后面左对齐，营地页的「刷新」也一并改掉了。

## 5. 保留的补丁

`Patches/CubicleSetPatch.cs` 仍然保留：它接管 `Cubicle_Helper.SetCubicle`，
把「是不是自己人」放宽成「前排 + 后备队」。本作里它不会被执行，
但如果哪天 Harmony 恢复可用，游戏内点选就能直接上工位，不用绕到面板。

## 6. 使用步骤

1. 面板「旅人」页 → 旅人列表里点某个人的「选」（休息区旅人也可以）；
2. 到下面「工位分配」里找到目标工位 → 点「安排」；
3. 底部会提示「某人 已换到操作中，某人 去了休息区 → 某工位」；
   旅人列表里那个人会从「休息区」变「操作中」、状态变「在岗」。

也可以不进「工位分配」：直接在列表里点「上阵」把人换到前排，
再用游戏自己的方式（工位面板里点工位）让他上工。

旅人处于昏迷 / 眩晕（`Character.state != null`）时会被拒绝，
这是游戏自己的规则，面板「旅人列表」里能看到每个人的状态。

## 6.1 怎么确认真的生效

游戏内点右上角的「交叉刀剑」图标（工位 / 装备面板）：
底部「操作中」「休息区」两排头像会跟着变，设备下面那些小格子里会出现干活的人。

## 7. 晕车（冲击昏迷）与免疫

### 7.1 游戏原本的机制

```
CharacterMgr.tick()                               CharacterMgr.cs:61-72
  ├── character_focus_aceleration 由车辆纵向加速度驱动
  │     （第 56 行还会减去 global_car_shock_absorb 的减震量）
  ├── shockForce = |character_focus_aceleration.y|
  └── 对每个前排旅人：Character.ApplyShockForce(shockForce)

Character.ApplyShockForce                         Character.cs:221-246
  ├── isImmuneToStun / state != null / coma_free_ticks > 0 → 直接返回
  ├── 阈值 num = desc.coma_g * (1 + global_coma_resist_pts/1000)
  ├── shockForce <= num → 不晕（会说一句台词）
  └── shockForce >  num → 按概率写入 state = new Coma(this, ...)
```

要点：

- **`ApplyShockForce` 是全游戏唯一 `new Coma` 的地方**（已全量 grep 确认），
  所以它就是「晕车」的唯一开关点。
- 只有**前排（`mgr.characters`）**旅人会参与这个判定，休息区的不受影响。
- 昏迷结束后 `Coma.end()` 会写 `coma_free_ticks = 3.5 秒 × 120`，
  所以不会「刚醒又立刻晕」。
- 旅人特性 `CP_Step_Up`（挺身而出）在**设备受击**时也会调 `ApplyShockForce`
  （`CP_Step_Up.cs:24-33`），所以同一个入口也负责「被设备震晕」。

### 7.2 本 Mod 的做法（v0.2.1 起：补「油门焊死」词缀）

v0.2.0 是给 `Character.ApplyShockForce` 挂前置补丁跳过整个方法，实测无效
（原因见第 4.1 节：Harmony 在本作不执行）。

现在改成改数据：给每个旅人补一份游戏自带的 **「油门焊死」** 词缀
（`CP_Reckless_Driving`，运行时从 `propertiess.records` 里按 `script` 名找到，实测 id = 162004）：

```csharp
// CP_Reckless_Driving.cs:16-20
public override void EnterTeam()
{
    owner.isImmuneToStun = true;                                   // ← 这就是免疫晕车
    Singleton<BattleContext>.instance.wheel_tractive_force_role += wheel_tf;
}
```

`CharacterGuardService` 的流程：

| 时机 | 动作 |
|---|---|
| 开关打开 | 对每个旅人：没有该词缀就 `CharacterUtility.GetProperty` → `Init` / `Start` / 加进 `character_properties` / `EnterTeam()`，并记进 `Injected` |
| 每 0.5 秒 | 轮询兜底：新入队、换人、读档后自动补齐（已有词缀的人只确认 `isImmuneToStun = true`） |
| 开关关闭 | 只对 `Injected` 里的人 `ExitTeam()` + 从列表移除，旅人自带的词缀不动 |
| 换局 / 读档 | 检测到 `CharacterMgr` 引用变化就清空 `Injected`（旧 Character 已废弃，不能再调它的 `ExitTeam`） |
| 词缀表还没就绪 | 直接 `isImmuneToStun = true` 兜底，保证功能立刻可用 |

要点：

- 词缀会随存档保存，读档后 `CharacterPD.use_current_data` 会重建 `character_properties`
  并调 `EnterTeam()`，所以免疫效果自动恢复，面板会显示「队伍里 N 人已有」；
- 副作用：词缀本身会给车轮加牵引力（`wheel_tractive_force_role += wheel_tf`），
  这是游戏数据原本的设计，不是本 Mod 加的；
- `isImmuneToStun` 只在 `ApplyShockForce` 里被读，全量 grep 确认游戏里只有
  `CP_Reckless_Driving` 会写它，所以关闭开关时把没词缀的人设回 `false` 是安全的。

### 7.3 「全部唤醒」

`CharacterGuardService.WakeAll()` 遍历前排 + 休息区，对 `state is Coma` 的旅人执行
`state.end(); state = null;` —— 和游戏自然结束昏迷的路径完全一致，
`end()` 会顺手写好 3.5 秒免疫。只清昏迷，不动 `Galvanized`（亢奋）等其它状态。

视图（`CharacterView`）是在 hover / 点击时**按需读** `character.state` 的，
所以清完不需要通知 UI，下一次交互就会显示正常。
